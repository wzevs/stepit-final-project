Galaxy Express

საკურიერო პლატფორმა მაღაზიისთვის, კერძო გამგზავნისთვის და კომპანიისთვის.

Python · Django · PostgreSQL

ისრები ან სივრცე — სლაიდი. N — სალაპარაკო ტექსტი. ცხრილები: tables.html

გამარჯობა. ავაწყე Galaxy Express — ერთი სისტემა, სადაც მაღაზია აგზავნის ამანათს, კურიერი მიჰქვს, კომპანია ხედავს რუკას და ფასს, მიმღები კი ნომრით ადევნებს თვალს. ბაზა PostgreSQL-ია და ფასის წესები იქ ცხოვრობს.

01

ოთხი მომხმარებელი, ერთი ამანათი

სტუმარი

კარიდან კარამდე აგზავნის /send/-ზე. წინასწარ იხდის. რუკაზე პინი აუცილებელია.

მაღაზია

ფილიალიდან აგზავნის ხელით ან X-API-Key-ით. შეუძლია COD, ანუ თანხა კურიერთან.

კურიერი

რუკაზე ხედავს ამანათს, სტატუსს ცვლის და წერტილს აგზავნის. ავტორიზაცია JWT-ითაა.

კომპანია

მაღაზიებს, კურიერებს, საწყობებს და ტარიფს მართავს. დისპეტჩერის რუკა ცოცხალია.

ოთხი კარი ერთ ამანათზე იყრის თავს. სტუმარი და მაღაზია ქმნის, კურიერი მიჰქვს, კომპანია აკონტროლებს ფასს და მარშრუტს. მიმღები ცალკე ანგარიში არ არის — ლინკით შედის.

ფასი ბაზიდან

ქსელი

ქალაქი, უბანი, ქალაქის საწყობი, უბნის საწყობი, მაღაზიის ფილიალი და საათები.

ცოცხალი რუკა

WebSocket, გაწყვეტისას HTTP გამოკითხვა. შეტყობინება მიდის ფოსტით და SMS-ით.

Android აპი ჯერ არ არის. კურიერის API და ბრაუზერის რუკა მზადაა, ამიტომ დემო ბრაუზერიდან მიდის. Telegram ამოღებულია — არხებია Gmail და uBill.

03

როგორ დგას

სერვერი

Django 5.2 და Django REST Framework. პანელები სესიით შედის, კურიერის რუკა JWT-ით, მაღაზიის პროგრამა API გასაღებით.

ბაზა

PostgreSQL. CHECK, უნიკალური წესი, ორი PL/pgSQL ტრიგერი და სამი VIEW. SQLite მხოლოდ სარეზერვოა, თუ Postgres არ დგას.

რუკა

Leaflet. პინს ფორმა ითხოვს. ქუჩის სახელით ძებნა მხოლოდ მაღაზიის API-ზეა, Nominatim-ით.

აპები: accounts, companies, clients, couriers, shipments, tracking, network, notifications, integrations.

სამი ავტორიზაცია სამი მიზეზითაა. პანელს სესია ჰყოფნის. კურიერის ტაბი JWT-ს ინახავს, რომ დისპეტჩერის ქუქი არ წაიშალოს. მაღაზიის საიტი გასაღებით იძახებს, პაროლის გარეშე.

05 · ბაზა

CHECK და უნიკალურობა

  1. ქალაქის საწყობს უბანი არ აქვს. უბნის საწყობს უბანი აუცილებლად აქვს. ეს warehouse_kind_matches_district-ია.
  2. ტარიფის ფორმა სახეობას ემთხვევა: სტანდარტულს და სახლამდე მიტანას ადგილი არ აქვს, ქალაქის წყვილს მხოლოდ ქალაქები, უბნის წყვილს მხოლოდ უბნები.
  3. კომპანიას ერთი სტანდარტული ფასი აქვს და ერთი სახლამდე დანამატი. ერთი წყვილი ორჯერ არ იწერება.
  4. წონის საფეხურზე ზედა ზღვარი ქვედაზე მაღალია. ნაღდის ჩანაწერზე თანხა ნულზე მეტია.
ეს წესები PostgreSQL-ის CHECK-ია. ფორმა რომ გვერდი აუაროს, ბაზა მაინც არ ჩაწერს არასწორ რიგს. უნიკალური ინდექსი ნაწილობრივია: მხოლოდ standard რიგებზე, მხოლოდ home რიგებზე, მხოლოდ city წყვილზე.

06 · ბაზა

ორი ტრიგერი, რადგან CHECK ორ ცხრილს ვერ ადარებს

warehouse_district_city

network_warehouse-ზე, ჩაწერამდე. თუ უბანი შევსებულია, მისი ქალაქი უნდა ემთხვეოდეს საწყობის ქალაქს. სხვა შემთხვევაში PL/pgSQL აგდებს შეცდომას.

warehouse_same_company

shipments_shipment-ზე, ჩაწერამდე. გატანის საწყობი უნდა ეკუთვნოდეს იმავე კომპანიას, რაც ამანათს. სხვისი საწყობი ვერ მიებმება.

ორივე არის BEFORE INSERT OR UPDATE. კოდი დგას apps/network/migrations/0002_places_views_and_trigger.py და apps/shipments/migrations/0005_promise_pod_and_ledger.py.

CHECK ხედავს ერთ რიგს: უბნის ველი ცარიელია თუ არა. იმას, რომ ეს უბანი სწორედ ამ ქალაქისაა, მხოლოდ მეორე ცხრილიდან იგებს. ამისთვისაა ტრიგერი. იგივე ლოგიკაა კომპანიაზე: ამანათის company_id და საწყობის company_id უნდა დაემთხვეს.

VIEW ინახება ბაზაში. cod_open_sheet მხოლოდ იმ ნაღდს აჩვენებს, რომელიც მაღაზიას ჯერ არ ჩაბარებია — settled_at ცარიელია.

ახლა VS Code-ის PostgreSQL კავშირში ან psql-ში ამ სამს ვუშვებ. სერვერი უკვე დგას, ცალკე SQL სერვერი არ მჭირდება. ბაზის სახელი .env-ის DATABASE_URL-ში წერია. ხედი იმიტომ, რომ პრეზენტაციაზე ქალაქის სახელი ჩანდეს და არა რიცხვი, და იგივე მოთხოვნა კოდის გარეშეც იმუშავებს.

08

ფასი ექვს ნაბიჯად ირჩევა

  1. უბანი → უბანი, თუ ორივე უბანი ცნობილია და ასეთი წესი არსებობს.
  2. თუ არა — ქალაქი → ქალაქი.
  3. თუ არც ის არის და მაღაზიას საკუთარი სტანდარტული აქვს — ის.
  4. თუ არც ის არის — კომპანიის სტანდარტული.
  5. წონის საფეხური ემატება. ქვედა კილოგრამი შედის, ზედა არა.
  6. სახლამდე მიტანა ბოლოს ემატება და მხოლოდ კარზე. საწყობიდან გატანას ეს დანამატი არ აქვს.

shipping_fee, route_fee, weight_fee, home_fee, tariff_basis ამანათზე რჩება.

კონკრეტული წესი ზოგადზე მარჯვია. ვაკედან საბურთალომდე უბნის ფასია, თუნდაც ქალაქის ფასიც არსებობდეს. თანხა ამანათზე იმიტომ იწერება, რომ ხვალ ტარიფს რომ შევცვლი, გუშინდელ გზავნილს ფასი არ გადაეწეროს. კოდი არის apps/network/quote.py.

09 · დემო

რა თანმიმდევრობით გავხსნა

  2. /send/ — სტუმრის გაგზავნა, ორი პინი რუკაზე.
  3. მაღაზია, /dashboard/ — ფილიალი, ახალი ამანათი, ფასი შენახვამდე.

11

რას ვიტყვი, თუ იკითხავენ

რატომ VIEW?

სახელებს აერთებს id-ების მაგივრად. მოთხოვნა ბაზაში რჩება და პრეზენტაციაზე ხელახლა აღარ იწერება.

რატომ ტრიგერი?

CHECK ერთ რიგს ხედავს. უბანი ამ ქალაქისაა თუ არა, მეორე ცხრილიდან იგება.

რატომ იწერება ფასი ამანათზე?

ტარიფის მომდევნო ცვლილება ძველ გზავნილს აღარ გადააწერს.

რა აკლია?

ნატიური Android აპი. JWT API და FCM-ის წერტილი უკვე არის. დემო ბრაუზერის კურიერის რუკით მიდის.

თუ იკითხავენ SQLite-ზე: დაცვა PostgreSQL-ზეა. SQLite მხოლოდ მაშინ ერთვება, როცა DATABASE_URL ცარიელია, და ტრიგერები იქ არ დგება. თუ იკითხავენ ტოკენზე: ბაზაში ნედლი ტოკენი არ ინახება, მხოლოდ ჰეში. მკვდარი ლინკი 404-ს აბრუნებს.

მზადება

დაცვამდე, ამ ოთახში

  1. PostgreSQL ჩართე და ერთხელ გაუშვი სამი SELECT, რომ ხედები ცარიელი არ იყოს.
  2. python manage.py runserver. გახსენი მთავარი, მაღაზია, მენეჯერი და კურიერი — პაროლები წინასწარ შეამოწმე.
  3. ერთი ამანათი წინასწარ გაიყვანე „გზაშია“ სტატუსამდე, რომ რუკა დემოს წამს ცარიელი არ იყოს.
  4. VS Code-ში გახსენი quote.py და ტრიგერის მიგრაცია. ბრაუზერში ეს სლაიდები და tables.html.
  5. დისპეტჩერი და კურიერი სხვადასხვა ბრაუზერში იყოს.
ეს სლაიდი დარბაზში არ ვაჩვენებ. სახლში რეპეტიცია ამ რიგით გავიარო ერთხელ, ხმამაღლა, საათით. სამიზნე ათი–თორმეტი წუთია, მერე კითხვები.
